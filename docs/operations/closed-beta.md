# Closed Beta 운영

이 문서는 베타 운영에 특화된 두 가지 — 베타 사용자 초대 절차, 안전한 베타 중단 절차 — 와 심각도 분류를 다룹니다. 그 외 운영 항목(작업 큐 점검, 헬스체크, 백업/복구, AI 제공자 상태 확인 등)은 이미 [monitoring.md](./monitoring.md), [batch-jobs.md](./batch-jobs.md), [checklists.md](./checklists.md), [ai-platform.md](./ai-platform.md), [backup.md](./backup.md), [restore.md](./restore.md), [disaster-recovery.md](./disaster-recovery.md)에 문서화되어 있으므로 여기서는 참조만 하고 반복하지 않습니다.

## 0. 심각도 분류 (P0-P3)

| 등급 | 정의 | 조치 |
|---|---|---|
| **P0** | 조직 간 데이터 노출, credential 노출, 복구 불가능한 데이터 손상/유실, 인가 우회(권한 없이 접근 성공) | **즉시 베타 중단** — 아래 "1. 베타 중단 절차" 실행 후 [incident-response.md](./incident-response.md) 절차로 진입 |
| **P1** | 가입/로그인 광범위 장애, 업로드 광범위 장애, 추출 광범위 장애, AI 광범위 이용 불가, 인용(citation)이 체계적으로 잘못됨 | 신규 사용자 초대 중단, 안정화 후 재개(베타 자체를 반드시 중단할 필요는 없음 — 이미 참여 중인 사용자에게 계속 서비스할지는 영향 범위에 따라 판단) |
| **P2** | 개별 워크플로 실패, 퍼널 완료를 크게 저해하는 UX 혼란, 복구 가능한 개별 작업 실패 | 정상 운영하며 다음 스프린트에서 수정 |
| **P3** | 사소한 표시 문제, 문구 오류, 낮은 우선순위 관리자 UX | 베타를 지연시키는 이유가 되지 않음 |

P0가 발생하면 "의심"만으로도 즉시 아래 절차를 실행합니다 — 확인을 기다리며 지체하지 않습니다.

## 1. 베타 중단 절차 (P0 대응, 또는 자발적 중단)

이 애플리케이션에 전용 "베타 정지 스위치"는 없으므로, 아래는 이미 존재하는 컨트롤을 조합한 순서입니다.

1. **신규 사용자 초대 중단**: 가입 자체는 오픈 셀프서비스이며 초대 코드/승인 게이트가 없습니다(§2 참고) — 중단은 절차적으로, 신규 사용자에게 가입 URL을 공유하지 않는 것으로 이루어집니다. 이미 공유된 URL을 기술적으로 차단하려면 리버스 프록시에서 `/signup` 경로를 일시 차단합니다.
2. **AI 비활성화**: `Organization.aiEnabled`는 조직별 플래그이며 전역 스위치는 없습니다. 베타 전체에서 AI를 끄려면 현재 초대된 베타 조직 전체를 대상으로 실행합니다:
   ```sql
   UPDATE organizations SET "aiEnabled" = false
   WHERE id IN (<현재 베타 조직 id 목록>);
   ```
   해제는 동일 쿼리에서 `= true`로 되돌립니다. `allowExternalAiProcessing = false`는 별도로 "AI 자체는 켜져 있지만 외부 제공자로는 보내지 않음" 상태를 만듭니다(외부 유출이 의심될 때 더 정밀한 선택지).
3. **워커 중단(필요 시)**: `extraction:process`/`clauses:process`/`ai:process-embeddings`/`ai:process-chunk-embeddings` 등은 외부 cron/scheduler가 트리거하는 CLI 스크립트입니다([batch-jobs.md](./batch-jobs.md) - 애플리케이션 자체에는 내장 워커 루프가 없습니다). 중단하려면 해당 cron 항목을 비활성화하거나 워커 프로세스/컨테이너를 정지시킵니다. PENDING 상태로 남은 작업은 데이터 손실 없이 그대로 대기하며, 워커를 재개하면 이어서 처리됩니다.
4. **로그/증거 보존**: 의심스러운 사고라면 [incident-response.md](./incident-response.md) §4(`retention:purge` 일시 중단, 로그/`audit_logs` 별도 백업)를 즉시 실행합니다.
5. **데이터 파괴 금지**: 이 단계에서는 어떤 데이터도 삭제하지 않습니다 — 중단은 접근/처리를 멈추는 것이지 데이터를 지우는 것이 아닙니다.
6. **영향받은 조직 식별**: `audit_logs`를 `organizationId`/`action`/시간대로 조회해 영향 범위를 좁힙니다(예: 특정 시간대에 발생한 `AI_CLAUSE_REVIEW_GENERATED`/`EXTRACTION_JOB_CREATED` 등). 의심되는 테넌트 격리 사고라면 아래 §2를 따릅니다.
7. **테넌트 격리 재검증**: 재개 전 `tests/integration/*tenant-isolation*.test.ts`(및 관련 cross-tenant 테스트)를 재실행해 격리가 깨지지 않았음을 확인합니다.
8. **서비스 복원**: 원인이 코드 결함이면 수정 배포 후, 인프라/설정 문제면 원상 복구 후 §0의 반대 순서로 되돌립니다(워커 재개 → AI 재활성화 → 초대 재개).
9. **복구 검증**: 복원 직후 `/api/health/ready`, `pnpm test:e2e:prod`(또는 최소한 핵심 퍼널의 수동 점검), 격리 테스트 재실행으로 정상 여부를 확인합니다.
10. **의도적 재개**: 8~9가 모두 통과한 뒤에만, 그리고 사후 분석([incident-response.md](./incident-response.md) §9)이 완료된 뒤에만 신규 사용자 초대를 재개합니다 — "일단 지켜보자"는 재개 사유가 될 수 없습니다.

## 2. 베타 사용자 초대/승인 방법

- 가입은 셀프서비스이며(`/signup`), 초대 코드나 관리자 승인 게이트가 코드베이스에 존재하지 않습니다 — 새로 구현하지 않았습니다(요청되지 않은 게이트 기능을 임의로 추가하지 않는다는 원칙).
- 따라서 베타 코호트 통제는 순수하게 운영 절차로 이루어집니다: **가입 URL을 선정한 사용자에게만 개별적으로 공유**합니다(예: 처음 2명, 문제 없으면 5명, 그다음 10명 순으로 단계적 확대).
- 기존 조직에 팀원을 추가로 초대하는 것은 이미 구현된 기능입니다: 조직 설정 → 팀원 초대(`invite-member-form.tsx` → `create-invitation-action.ts`) → 초대 이메일 발송 → 수락 시 계정 생성/합류. 이는 "이미 베타에 참여 중인 조직이 자기 팀원을 늘리는" 경우에만 해당하며, 새 조직(새 회사)을 베타에 들이는 것과는 다른 절차입니다(새 조직은 그냥 `/signup`으로 직접 가입).
- 가입 성공 확인: `audit_logs`에서 `action = 'ORGANIZATION_CREATED'`를 조회하거나, 로그인 성공은 `action = 'USER_LOGIN'`으로 확인합니다.

## 3. 테넌트 격리 사고 대응 (P0 하위 항목)

기술적 절차는 [incident-response.md](./incident-response.md)를 그대로 따르되, 테넌트 격리 사고에 특화된 순서는 다음과 같습니다.

1. 위 §1의 "베타 중단 절차"를 즉시 실행합니다(신규 초대 중단은 필수, AI 비활성화는 노출 경로가 AI 검색/인용이라면 특히 우선).
2. 어떤 조직이 어떤 조직의 데이터를 봤는지 `audit_logs` + 애플리케이션 로그(요청 경로, 시간대)로 재구성합니다. 계약 본문/조항 원문은 로그에 없으므로, 노출된 "내용"이 아니라 노출된 "사실"(어떤 entityId가 어떤 조직 컨텍스트에서 접근됐는지)만 로그로 재구성 가능하다는 한계를 감안합니다.
3. 영향받은 조직에는 사실을 알리고 원본 소유 조직에도 통지 여부를 판단합니다(법적 판단 필요 시 별도 법무 검토 - [incident-response.md](./incident-response.md) 서문 참고).
4. 원인이 된 쿼리/캐시 키/검색 경로를 특정하고, 회귀 테스트(바이트 단위로 동일한 미끼 콘텐츠를 두 조직에 넣고 교차 접근이 불가능함을 확인하는 형태)를 추가한 뒤에만 재개합니다.
