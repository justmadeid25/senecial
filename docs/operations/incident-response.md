# 사고 대응 기본 절차

실제 법적 신고 의무(개인정보 유출 신고 등)는 관할과 상황에 따라 다르므로, 아래 절차는 기술적 대응만 다룹니다 — 법적 판단이 필요하면 별도로 법무 검토를 거치십시오.

**Closed Beta 심각도 분류(P0-P3)와 베타 중단 절차는 [closed-beta.md](./closed-beta.md)를 먼저 확인하십시오** — 이 문서는 사고가 확인된 *이후*의 기술적 대응 절차이며, "지금 베타를 멈춰야 하는가"의 판단 기준과 중단 자체를 실행하는 순서는 closed-beta.md §0/§1에 있습니다.

## 1. 사고 확인

- 증상을 구체적으로 기록(언제, 무엇을, 어떻게 발견했는지)
- `/api/health/ready` 확인, `batch_executions`/`audit_logs` 최근 이력 확인
- 영향 범위 추정(특정 조직만인지, 전체인지)

## 2. 영향 범위 제한

- 의심되는 계정/조직이 있다면 해당 사용자의 세션을 무효화 (`User.sessionVersion`을 수동으로 증가시키면 기존 JWT가 즉시 무효화됨):
  ```sql
  UPDATE users SET "sessionVersion" = "sessionVersion" + 1 WHERE id = '<userId>';
  ```
- 필요하다면 애플리케이션을 유지보수 모드로 전환(리버스 프록시에서 일시 차단)하거나, 특정 IP/조직의 접근을 프록시 레벨에서 차단

## 3. Credential Rotation

`security.md`의 rotation 절차를 따라 다음을 즉시 교체하는 것을 검토하십시오.

- `AUTH_SECRET` (모든 세션 강제 무효화가 필요한 경우)
- `DATABASE_URL`의 DB 비밀번호
- 연동된 외부 공급자 API 키(향후 실제 공급자 연동 시)

## 4. 로그 보존

- 사고 조사에 필요한 로그(구조화 JSON 로그, `audit_logs` 테이블)를 사고 조사가 끝날 때까지 삭제되지 않도록 별도로 백업/보존하십시오.
- **retention:purge를 사고 조사 기간 동안 일시 중단**하십시오(스케줄러에서 해당 cron을 비활성화) — AuditLog나 관련 데이터가 조사 도중 삭제되는 것을 방지합니다.

## 5. 백업 보호

- 사고 발생 시점 전후의 백업을 별도 위치에 복사해 자동 정리/덮어쓰기로부터 보호하십시오.

## 6. 사용자 접근 차단 여부

- 확산 방지가 필요하면 해당 조직/사용자의 로그인을 막을지 판단하십시오(현재 애플리케이션에는 계정 잠금 기능이 없으므로, 필요하다면 `passwordHash`를 임의 값으로 교체해 사실상 로그인 불가 상태로 만들고 별도로 사용자에게 안내하는 방식을 고려).

## 7. 데이터 무결성 점검

```bash
pnpm restore:verify --manifest=<가장 최근 정상 백업의 manifest> --target-database-url=<검증용 임시 DB>
```
를 이용해 의심되는 시점 이전 백업과 현재 데이터를 비교하는 것도 방법입니다(임시 DB에 복구 후 비교 쿼리 실행).

## 8. 복구

- `restore.md`/`disaster-recovery.md` 절차를 따르되, 복구 대상 시점을 사고 발생 *이전*으로 명확히 하십시오.
- 부분 복구(특정 조직만)가 필요한 경우 현재 restore 스크립트는 DB 전체 단위로만 동작합니다 — 조직 단위 선택 복구는 별도 수작업(임시 DB에 전체 복구 후 해당 조직 데이터만 추출)이 필요합니다.

## 9. 사후 분석

- 타임라인 정리(발견 → 조치 → 복구)
- 근본 원인
- 재발 방지 조치(코드 수정, 모니터링 추가, 프로세스 변경)
- 관련자 공유
